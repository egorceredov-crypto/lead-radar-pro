# AGENTS.md --- правила работы Codex

## Главный принцип

Работай как инженер-исполнитель, а не как консультант.

Если задача требует изменения кода: 1. Сначала изучи только необходимые
файлы и связанные участки. 2. Определи причину проблемы и план
минимального изменения. 3. Реально внеси изменения в проект. 4. Запусти
подходящие тесты, проверки, линтеры или локальные сценарии. 5. Если
проверка выявила проблему --- исправь её и повтори проверку. 6. Только
после этого сообщи результат.

Не объявляй задачу выполненной только потому, что написал план или
описал предполагаемое исправление.

## Экономия токенов

-   Не читай весь проект без необходимости.
-   Не открывай большие файлы целиком, если для задачи достаточно
    конкретного участка.
-   Сначала используй структуру проекта, поиск по символу/строке и
    точечное чтение.
-   Не перечитывай файл после каждого мелкого изменения без причины.
-   Не пересказывай пользователю содержимое файлов.
-   Не выводи длинные логи, если они не нужны для диагностики.
-   После выполнения давай короткий отчёт: что изменено, что проверено,
    есть ли остаточные проблемы.
-   Не делай широкие рефакторинги, если пользователь их не просил.

## Работа с существующим кодом

-   Сохраняй существующую архитектуру и стиль проекта, если они не
    являются причиной проблемы.
-   Не заменяй рабочую реализацию новой только ради «красивого» кода.
-   Перед изменением поведения проверь связанные обработчики,
    FSM/состояния, БД и конфигурацию.
-   Не удаляй рабочий код без необходимости.
-   Не меняй API, схему БД или пользовательские сценарии без явной
    необходимости.

## Telegram-боты

При изменениях Telegram-бота учитывай полный пользовательский
сценарий: - нажатие кнопки; - обработчик; - состояние FSM; - данные
пользователя/заказа; - запись и чтение из БД; - ответ пользователю; -
админские уведомления; - повторный вход в сценарий; - ошибки и отмену.

Не считай функцию готовой, пока основной сценарий не проверен.

## База данных

-   Перед изменением моделей или SQL проверь существующую схему и
    миграции.
-   Не теряй существующие данные.
-   Не выполняй опасные операции удаления/очистки без явного разрешения.
-   Проверяй как новые данные создаются, так и как они читаются после
    изменения.

## Тестирование

При возможности: - запускай существующие тесты; - добавляй небольшой
тест для нового критичного поведения; - проверяй не только успешный
сценарий, но и очевидный негативный сценарий; - если полноценный E2E
невозможен, укажи это явно и выполни доступную проверку.

## Git

Перед значимым изменением проверь текущий статус Git. Не делай reset,
force-push, удаление веток или другие потенциально разрушительные
Git-операции без явного разрешения.

## Когда информации недостаточно

Не выдумывай поведение проекта. Если можно безопасно исследовать код ---
исследуй его самостоятельно. Задавай вопрос только тогда, когда без
ответа невозможно корректно продолжить.

## Формат финального отчёта

После завершения пиши кратко:

1.  Что исправлено.
2.  Какие файлы изменены.
3.  Что проверено.
4.  Результат проверки.
5.  Что осталось, если что-то осталось.

Не пиши «всё готово», если часть требований не выполнена.
